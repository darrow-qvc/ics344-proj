# 2. Job control: process groups, terminal handoff, signals

Owner: Husain Althagafi (`src/jobs/`). Answers feedback items 2 and 3.

## 2.1 Terms

- **Job**: one pipeline, foreground or background. One entry in the job
  table (`struct ms_job`), one process group.
- **Process group (pgid)**: all processes of a job share a pgid equal to the
  pid of the first stage. Signals from the terminal and from `kill(-pgid)`
  reach every stage at once.
- **Foreground process group of the terminal**: the one group whose
  processes may read the terminal and that receives SIGINT/SIGTSTP/SIGQUIT
  generated by Ctrl+C / Ctrl+Z / Ctrl+\. Set with `tcsetpgrp()`.

## 2.2 Shell start-up (`ms_jobs_init`, interactive only)

```
1  loop:  fg = tcgetpgrp(tty); if fg == getpgrp() break;
          kill(-getpgrp(), SIGTTIN)             -- we were started in the
                                                   background: stop until fg
2  ignore SIGINT SIGQUIT SIGTSTP SIGTTIN SIGTTOU  -- the shell itself must
                                                   never die or stop on keys
3  sigaction(SIGCHLD, handler, SA_RESTART)        -- NOT SA_NOCLDSTOP:
                                                   we need stop/continue news
4  setpgid(0, 0)                                  -- own process group
5  tcsetpgrp(tty, getpgrp()); tcgetattr(tty, &ms_shell_tmodes)
```

Interactive means stdin and stdout are terminals. When stdin is a pipe or
file (tests, scripts, `-c`) steps 1, 2, 4, 5 are skipped, exactly as bash
disables job control for scripts; `&`, `jobs`, `fg`, `bg` and SIGCHLD
reaping still work, only terminal ownership is not touched.

## 2.3 Launching a job: exact sequence

`ms_run_pipeline` (io module) drives it; the jobs module provides the
pieces. Time flows downwards; `P` is the shell, `C1..Cn` the stages.

```
P   sigprocmask(BLOCK, {SIGCHLD})                 (a)
P   job = ms_job_add(text)                        (b)  slot reserved, pgid = 0
P   for each stage i:
P       pipe()                                    (c)
P       pid = fork()
Ci      ms_child_setup(job->pgid, foreground):
Ci          pgid = job->pgid ? job->pgid : getpid()
Ci          setpgid(getpid(), pgid)               (d)  first child becomes leader
Ci          if foreground: tcsetpgrp(tty, pgid)   (e)  SIGTTOU still ignored here,
                                                       so this cannot stop us
Ci          SIGINT SIGQUIT SIGTSTP SIGTTIN SIGTTOU SIGCHLD -> SIG_DFL   (f)
Ci          sigprocmask(SETMASK, {})              (g)  undo (a) in the child
Ci      wire pipes, apply redirections, execvp
P       ms_parent_setup(job, pid):
P           if job->pgid == 0: job->pgid = pid
P           setpgid(pid, job->pgid)               (d') same call as (d): whichever
                                                       side runs first wins
P           ms_job_add_proc(job, pid)             (h)  pid now in the table
P       close parent's copies of pipe ends
P   if background:  ms_job_background(); print "[n] pid"
P   else:           ms_job_foreground(job):
P       tcsetpgrp(tty, job->pgid)                 (i)  terminal to the job
P       while job->state == RUNNING:
P           sigsuspend(mask without SIGCHLD)      (j)  atomically unblock + sleep
P       tcsetpgrp(tty, ms_shell_pgid)             (k)  terminal back to the shell
P       if stopped: tcgetattr(tty, &job->tmodes)  (l)  remember the job's modes
P       tcsetattr(tty, TCSADRAIN, &ms_shell_tmodes) (m) restore the shell's modes
P   sigprocmask(SETMASK, saved)                   (n)  undo (a)
```

Why both (d) and (d'): after `fork()` nobody knows whether parent or child
runs first. If only the child called `setpgid`, the parent's `tcsetpgrp`
at (i) could name a group that does not exist yet. If only the parent did
it, the child could `execvp` first and the call would fail with EACCES.
Doing it on both sides makes the order irrelevant; the "loser" gets EACCES
(child already exec'd) or ESRCH (child already exited), both ignored.

Why (e) and (i) both: same reason. The child's call guarantees the job
owns the terminal before it execs; the parent's call guarantees it even if
the child has already exited (so a stopped later stage can still be
resumed with the terminal).

Why `TCSADRAIN` at (m): it waits for the job's pending output to drain
before the shell's modes (echo, canonical) are restored, so the prompt is
not corrupted.

### Resuming with `fg`

`fg` calls `ms_job_foreground(job, cont=1)`: (i), then
`tcsetattr(tty, TCSADRAIN, &job->tmodes)` to give back the modes the job
had when stopped (an editor's raw mode, for example), then
`kill(-pgid, SIGCONT)`, then (j) to (m) as above. `bg` sends SIGCONT and
marks the job running without touching the terminal.

## 2.4 SIGINT and SIGTSTP delivery

The tty driver turns Ctrl+C into SIGINT and Ctrl+Z into SIGTSTP and sends
them to **every process in the terminal's foreground process group**, and
nothing else. Three facts make this safe:

1. While a foreground job runs, the foreground group is the job's (step
   (i)). The shell and all background jobs are in other groups and never
   see the signal.
2. The shell ignores these signals anyway (start-up step 2), so even a
   signal raised by `kill` cannot kill or stop the shell.
3. Children reset the dispositions to default (f) **before** `execvp`, so
   the program gets the normal behaviour: Ctrl+C terminates, Ctrl+Z stops.
   Because (f) happens after (e), the child never has SIGTTOU default while
   it calls `tcsetpgrp` from a background group.

A background job that reads the terminal gets SIGTTIN from the kernel and
stops; the handler records it as Stopped and `jobs` shows it, as in bash.

`tests/pty_tests.py` verifies the ownership with `os.tcgetpgrp()` from the
outside: during `fg` the owner is not the shell, after Ctrl+Z or Ctrl+C it
is the shell again.

## 2.5 SIGCHLD handling and the job-table race

The handler:

```c
while ((pid = waitpid(-1, &status, WNOHANG | WUNTRACED | WCONTINUED)) > 0)
    ms_job_mark(pid, status);
```

- `WNOHANG`: never block inside a handler.
- `WUNTRACED`: report stopped children (Ctrl+Z, SIGSTOP, SIGTTIN).
- `WCONTINUED`: report continued children (`bg`, external SIGCONT), so the
  table flips back to Running without guessing.
- The loop: signals do not queue; one SIGCHLD can stand for several
  children (e.g. all three stages of a pipeline exit together).
- `ms_job_mark` only compares and assigns integers in a static array and
  is therefore async-signal-safe. Nothing is printed from the handler.

### The race and how it is closed

Without care, a child can exit **before** the parent has stored its pid:
the handler would then reap a pid that is not in the table and the job
would wait forever. The `tests/cases/10_quick_exit.sh` and
`quick_exiting_children_leave_no_zombies` tests exercise exactly this
with `/bin/true`.

The invariant is: **the main program touches the job table only while
SIGCHLD is blocked.** Concretely:

| operation | SIGCHLD state | why |
|---|---|---|
| `fork()` + `setpgid` + `ms_job_add_proc` (a..h) | blocked | the child cannot be reaped before its pid is stored |
| waiting for a foreground job (j) | blocked, except inside `sigsuspend` | `sigsuspend` unblocks and sleeps atomically; a SIGCHLD that became pending during (a..i) is delivered immediately, so a child that already exited is never missed and the state check after return sees it |
| `jobs`, `fg`, `bg`, `ms_jobs_notify` | blocked for the duration | a half-printed or half-updated entry is never observed |
| child after fork (g) | unblocked | the exec'd program must start with a clean mask |

Because the handler is the only reader of `waitpid`, there is no second
reaper to steal statuses, and because every child is in the table before
it can be reaped, every exit is attributed. The job is freed only when all
of its processes are done, so no zombie is left behind by an early stage
of a pipeline (`ps` shows none; see the pty test).

## 2.6 Job states

```
            fork            all exited
  (new) ---------> RUNNING ------------> DONE ---> freed after being reported
                    ^   |
     SIGCONT (bg/fg)|   | all live procs stopped (SIGTSTP/SIGSTOP/SIGTTIN)
                    |   v
                   STOPPED
```

Job exit status = status of the last process: `WEXITSTATUS`, or
`128 + signal` if killed by a signal, or `128 + SIGTSTP` (148) if stopped.

## 2.7 Known limitation

If the first stage of a pipeline exits before a later stage calls
`setpgid`, the process group may already be empty and `setpgid` fails with
EPERM; that stage then stays in the shell's group. bash has the same
window. It is harmless unless that stage reads the terminal directly,
which is why `tests/cases/10_quick_exit.sh` uses `true | true | true`.
